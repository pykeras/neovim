۰۰ نصب و پیش‌نیازها

این کانفیگ به Neovim نسخهٔ ۰٫۱۱ یا بالاتر نیاز دارد. نسخه‌های قدیمی‌تر نمی‌توانند mason-lspconfig نسخهٔ ۲ و venv-selector را بارگذاری کنند و در نتیجه هیچ LSP‌ای به فایل پایتون وصل نمی‌شود.

بررسی نسخه با nvim --version نسخه را چک کنید. اگر عدد کمتر از ۰٫۱۱ بود، اول Neovim را به‌روز کنید — بقیهٔ این راهنما بدون آن کار نخواهد کرد.

ابزارهای بیرونی

این‌ها باید در سیستم نصب باشند (نه داخل Neovim):

# مدیر پکیج و محیط مجازی — سریع‌ترین گزینهٔ فعلی
curl -LsSf https://astral.sh/uv/install.sh | sh

# لینتر و فرمترِ پایتون (بسیار سریع، جایگزین black + isort + flake8)
uv tool install ruff

# اجرای تست‌ها + دیباگر
uv tool install pytest
uv pip install debugpy

بقیهٔ ابزارها (pyrefly، ruff-lsp، stylua و …) را خود Mason موقع اولین اجرا نصب می‌کند. با :Mason وضعیتشان را ببینید و با :checkhealth از سالم بودن کل نصب مطمئن شوید.

نقش هر ابزار

pyreflyسرور زبان اصلی — تایپ‌چک، تعریف، ارجاع، تکمیل کد
ruffلینتر و فرمتر — سریع، جای black، isort و flake8 را می‌گیرد
debugpyموتور دیباگ که nvim-dap به آن وصل می‌شود
pytestاجراکنندهٔ تست که neotest صدا می‌زند

۰۱ محیط مجازی

این اولین کاری است که در هر پروژه باید انجام دهید. تا وقتی محیط مجازی انتخاب نشده، LSP پکیج‌های نصب‌شدهٔ پروژه را نمی‌شناسد و زیر هر import خط قرمز می‌کشد.

<leader>vsباز کردن انتخابگر محیط مجازی
<leader>vcانتخاب محیطی که قبلاً برای همین پروژه استفاده شده
نکته کلید <leader> در این کانفیگ همان Space است. پس <leader>vs یعنی: Space بعد v بعد s.

ساخت محیط جدید

uv venv                      # می‌سازد: .venv
uv pip install -r requirements.txt

# یا با pyproject.toml
uv sync

انتخابگر به‌طور خودکار دنبال پوشهٔ .venv می‌گردد، پس اگر محیط را با همین نام بسازید بدون تنظیم اضافی پیدا می‌شود.

۰۳ فرمت و ایمپورت

فرمت‌کردن موقع ذخیره به‌طور خودکار انجام می‌شود: ruff format و بعد ruff check --fix. پس معمولاً نیازی به زدن دستی کلید ندارید.

rfفرمت دستی فایل
<leader>oiمرتب‌سازی ایمپورت‌ها و حذف ایمپورت‌های بلااستفاده
<leader>faرفع همهٔ خطاهای قابل‌اصلاح خودکار

تنظیم قوانین در پروژه

یک فایل pyproject.toml در ریشهٔ پروژه بگذارید — هم Neovim و هم اجرای دستی ruff از آن پیروی می‌کنند: 

[tool.ruff]
line-length = 88
target-version = "py313"

[tool.ruff.lint]
# E,F پایه · I ایمپورت · UP نحو مدرن
# B باگ‌های رایج · SIM ساده‌سازی · RUF عمومی
select = ["E", "F", "I", "UP", "B", "SIM", "RUF"]

[tool.ruff.format]
quote-style = "double"

۰۴ حرکت ساختاری

این بخش بزرگ‌ترین تفاوت بین «تایپ‌کردن در Neovim» و «حرفه‌ای کدنوشتن» است. به‌جای حرکت خط‌به‌خط، مستقیم روی تابع، کلاس و آرگومان کار می‌کنید.

انتخاب

این‌ها بعد از v (انتخاب)، d (حذف)، c (تغییر) یا y (کپی) می‌آیند. مثلاً vif بدنهٔ تابع را انتخاب می‌کند.

af   ifکل تابع / فقط بدنهٔ تابع
ac   icکل کلاس / فقط بدنهٔ کلاس
aa   iaآرگومان — با یا بدون ویرگول
al   ilحلقه
ai   iiبلوک شرطی
a/کامنت

پرش و جابه‌جایی

]f   [fتابع بعدی / قبلی
]c   [cکلاس بعدی / قبلی
]a   [aآرگومان بعدی / قبلی
<leader>saجابه‌جایی این آرگومان با بعدی
<leader>sAجابه‌جایی این آرگومان با قبلی
ترکیب‌های پرکاربرد dif خالی‌کردن بدنهٔ تابع  ·  yac کپی کل کلاس  ·  cia عوض‌کردن یک آرگومان  ·  vaf سپس <leader>ca برای اکشن روی کل تابع.

۰۵ تست با pytest

تست‌ها بدون خروج از ادیتور اجرا می‌شوند و نتیجه به‌صورت علامت کنار شمارهٔ خط ظاهر می‌شود. کلیدها با <leader>n شروع می‌شوند.

<leader>nrاجرای نزدیک‌ترین تست به نشانگر
<leader>nFاجرای همهٔ تست‌های این فایل
<leader>naاجرای کل مجموعهٔ تست پروژه
<leader>nLاجرای دوبارهٔ آخرین تست
<leader>ndbدیباگ تست نزدیک — با breakpoint متوقف می‌شود
<leader>nxتوقف اجرای تست
<leader>noدیدن خروجی کامل تست شکست‌خورده
<leader>npپنل خروجی (زنده)

مهم neotest از همان محیط مجازی استفاده می‌کند که با <leader>vs انتخاب کرده‌اید. اگر تست‌ها با خطای ModuleNotFoundError شکست خوردند، اول محیط را انتخاب کنید.

۰۶ دیباگ

به‌جای پخش‌کردن print() در کد، اجرا را متوقف کنید و مقدار واقعی متغیرها را ببینید. رابط دیباگ خودکار باز و بسته می‌شود.

<leader>bگذاشتن / برداشتن breakpoint روی این خط
F6breakpoint شرطی — مثلاً i == 42
F5شروع اجرا / ادامه تا breakpoint بعدی
F3اجرای خط بعد (step over)
F2ورود به داخل تابع (step into)
F4خروج از تابع فعلی (step out)
F7پایان دادن به جلسهٔ دیباگ
F8اجرای دوبارهٔ آخرین پیکربندی
جریان معمول نشانگر را روی خط مشکوک ببرید ← <leader>b ← F5 ← وقتی متوقف شد در پنجرهٔ Scopes مقدار متغیرها را ببینید ← با F3 خط‌به‌خط جلو بروید.

۰۹ جریان کاری روزمره

ترتیبی که در عمل بیشترین بازدهی را می‌دهد:

  1. پروژه را باز کنید و فوراً با <leader>vs محیط مجازی را انتخاب کنید. بدون این کار بقیهٔ ابزارها ناقص کار می‌کنند.
  2. با <leader>ff یا Ctrl+p فایل را پیدا کنید؛ برای گشتن دنبال یک تابع از <leader>fg استفاده کنید.
  3. کد بنویسید. فایل خودکار ذخیره و فرمت می‌شود، پس نیازی به :w نیست.
  4. خطاها را با ]e دنبال کنید و با <leader>ca رفع کنید.
  5. با <leader>nr تست مربوطه را اجرا کنید. اگر شکست خورد، <leader>no خروجی کامل را نشان می‌دهد.
  6. اگر علت شکست روشن نبود، breakpoint بگذارید <leader>b و با <leader>ndb تست را دیباگ کنید.
  7. پیش از commit، <leader>xx را بزنید تا مطمئن شوید خطایی در کل پروژه باقی نمانده.

۱۰ ساختار پروژه

چیدمانی که ابزارهای بالا بدون تنظیم اضافی با آن کار می‌کنند — الگوی src/ که استاندارد پروژه‌های جدی پایتون است: 

myproject/
├── .venv/                # venv-selector خودکار پیدا می‌کند
├── src/
│   └── myproject/
│       ├── __init__.py
│       └── core.py
├── tests/
│   ├── conftest.py
│   └── test_core.py
├── pyproject.toml        # تنظیمات ruff + وابستگی‌ها
└── README.md

حداقل pyproject.toml

[project]
name = "myproject"
version = "0.1.0"
requires-python = ">=3.11"
dependencies = []

[build-system]
requires = ["hatchling"]
build-backend = "hatchling.build"

[tool.pytest.ini_options]
testpaths = ["tests"]
pythonpath = ["src"]
چرا src/ با این ساختار، تست‌ها ناچارند پکیج نصب‌شده را ایمپورت کنند نه فایل‌های کنار خودشان. نتیجه: خطاهای بسته‌بندی را موقع تست می‌بینید، نه بعد از انتشار.
